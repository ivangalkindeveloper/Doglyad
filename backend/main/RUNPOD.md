# RunPod — справочник по настройкам эндпоинтов

> **RunPod — резервный путь, а не основной.** Инференс идёт на собственные GPU-виртуалки (по одной на модель, см. [`backend/inference/README.md`](backend/inference/README.md)); бэкенд обращается к serverless-эндпоинту RunPod, только если запрос к виртуалке упал. Эндпоинты всё равно должны быть подняты и настроены — иначе резерва просто нет, и сбой виртуалки становится ошибкой у врача.
>
> Разбор настроек vLLM ниже применим и к GPU-виртуалкам: там те же значения задаются через `backend/inference/secrets/.env`.

Разбор каждой настройки из [`backend/main/config/runpod_endpoints.json`](backend/main/config/runpod_endpoints.json) — файла, описывающего желаемое состояние serverless-эндпоинтов, на которых крутится резервный инференс.

Применяется скриптом [`backend/main/scripts/runpod_sync.py`](backend/main/scripts/runpod_sync.py):

```
make runpod-plan     показать дифф, ничего не менять
make runpod-apply    привести RunPod к конфигу
make runpod-urls     достать текущие URL эндпоинтов
make runpod-destroy  удалить эндпоинты doglyad-*
```

## Как настройки попадают в RunPod

RunPod хранит конфигурацию эндпоинта в **двух разных объектах**, и это определяет всё остальное:

| Объект | Что в нём | Ручка API |
|---|---|---|
| **Template** (шаблон) | Docker-образ, диск, **все переменные окружения** | `PATCH /templates/{id}` |
| **Endpoint** (эндпоинт) | GPU, скейлинг, таймауты | `PATCH /endpoints/{id}` |

Эндпоинт ссылается на шаблон по `templateId`. Один шаблон + один эндпоинт на модель.

Практическое следствие: правка `MAX_MODEL_LEN` и правка `gpuCount` — это **два разных HTTP-запроса** к разным объектам. Изменение шаблона запускает rolling release: RunPod поднимает воркеры на новой версии и дренирует старые.

База API — `https://rest.runpod.io/v1`, авторизация `Authorization: Bearer <RUNPOD_ADMIN_API_KEY>`.

## Структура файла

```json
{
  "_comment": [ "..." ],
  "defaults": { "...общие настройки..." },
  "endpoints": {
    "google/medgemma-4b-it": { "...перекрытия..." }
  }
}
```

**`_comment`** — заметки для человека. Скрипт игнорирует ключи, начинающиеся с `_`.

**`defaults`** — подмешивается в каждый эндпоинт. Скалярные поля перекрываются целиком, а `env` **объединяется по ключам**: `defaults.env` + `endpoints.<id>.env`, где второе побеждает. Поэтому `MODEL_NAME` задаётся в каждой модели отдельно, а `MAX_MODEL_LEN` — один раз в `defaults`.

**`endpoints`** — ключи обязаны совпадать с `id` моделей из `ultrasound_examination_neural_models.json`. Скрипт это проверяет и падает, если модель показывается в приложении, но эндпоинта под неё нет.

**`${VAR}`** — подстановка из `backend/main/secrets/.env`. Секретов в этом файле нет и быть не должно: он лежит в git. Если переменной в `.env` не окажется, скрипт упадёт с явной ошибкой, а не подставит пустую строку.

**Имя эндпоинта** выводится из `id` модели: `google/medgemma-4b-it` → `doglyad-google-medgemma-4b-it` (слэш в имени недопустим). По этому имени скрипт находит существующий эндпоинт — переименуете в UI, и `apply` создаст дубль.

## Часть 1. Настройки шаблона

### `imageName`

> Дефолт RunPod: нет (обязательное поле) · У нас: `runpod/worker-v1-vllm:v2.23.0`

Docker-образ воркера. Мы используем [`runpod/worker-v1-vllm`](https://github.com/runpod-workers/worker-vllm) — официальную обёртку RunPod вокруг vLLM, которая превращает движок в serverless-обработчик.

Тег определяет сразу три вещи, и все три уже ломались:

1. **Версию vLLM.** Набор поддерживаемых переменных и поведение профилировщика памяти между версиями меняются. Версию работающего движка видно в логе воркера: `Initializing a V1 LLM engine (v0.23.0)`.
2. **Версию движка.** Старые сборки по умолчанию ставят `--guided-decoding-backend=outlines`, который не поддерживается V1, и молча откатываются на легаси-движок V0 — строкой `Falling back to V0` в логе.
3. **Поддерживаемые архитектуры GPU.** PyTorch внутри образа собран под конкретный набор compute capability. Сборка на CUDA 12.1 знает максимум `sm_90`, и на карте Blackwell (`sm_120`) любая модель падает с `no kernel image is available for execution on the device` — на первой же CUDA-операции, ещё до загрузки весов.

**Номер тега не совпадает с версией vLLM.** В ветке `v2.22.x` был откат с vLLM 0.21 обратно на 0.20.2, так что угадывать по номеру нельзя. Актуальные теги и то, что в них внутри, смотрите в [релизах](https://github.com/runpod-workers/worker-vllm/releases):

```bash
curl -s https://api.github.com/repos/runpod-workers/worker-vllm/releases/latest
```

Docker Hub отдаёт полный список тегов, но там же лежат служебные `dev-refs-pull-*`, `test-*` и `buildcache` — релизные отбираются по маске `^v[0-9]`:

```bash
curl -s "https://hub.docker.com/v2/repositories/runpod/worker-v1-vllm/tags?page_size=100&ordering=last_updated"
```

### `containerDiskInGb`

> Дефолт RunPod: `50` · У нас: `30`

Размер диска контейнера в гигабайтах. Сюда качаются веса модели с Hugging Face.

Нужно не меньше, чем весит чекпоинт, плюс запас на образ (~10 ГБ). Ориентир: модель в bf16 занимает примерно `2 байта × число параметров` — 4B ≈ 8 ГБ, 27B ≈ 54 ГБ. Для 27B тридцати гигабайт **не хватит**, диск нужно поднимать.

Диск оплачивается, поэтому смысла ставить с запасом в разы нет.

## Часть 2. `env` — переменные движка vLLM

Всё, что попадает в `env`, worker-vllm передаёт в vLLM. Кроме явно документированных переменных он [автоматически распознаёт любое поле `AsyncEngineArgs`](https://github.com/runpod-workers/worker-vllm/blob/main/README.md) по UPPERCASE-имени — то есть сюда можно прокинуть практически любой аргумент движка, даже если его нет в документации RunPod.

### `MODEL_NAME`

> Дефолт: `facebook/opt-125m` · У нас: id модели, свой для каждого эндпоинта

Репозиторий на Hugging Face или путь к весам. Единственная переменная, которая обязана задаваться в каждом блоке `endpoints` отдельно.

### `MAX_MODEL_LEN` — самая важная настройка

> Дефолт: не задан → берётся из конфига модели (у Gemma 3 это **131072**) · У нас: `16384`

Максимальная длина контекста в токенах. Влияет на три вещи сразу, и последняя — неочевидная и самая дорогая.

1. Потолок длины запроса.
2. Размер KV-кэша: движку нужно уметь разместить хотя бы одну последовательность максимальной длины.
3. **Бюджет encoder cache** — и через него количество изображений, которые прогоняются через визуальный энкодер на старте.

Третий пункт — причина, по которой этот проект вообще получил OOM. При запуске vLLM делает профилировочный прогон, чтобы измерить пик памяти. Для мультимодальной модели он берёт бюджет энкодера, равный `MAX_MODEL_LEN`, и заполняет его изображениями:

```
изображений на профилировке = MAX_MODEL_LEN / токенов_на_изображение
```

У Gemma 3 (и MedGemma) одно изображение — это **256 токенов**. При дефолтных 131072:

```
131072 / 256 = 512 изображений разом через SigLIP
```

Что в логе выглядит буквально так:

```
Encoder cache will be initialized with a budget of 131072 tokens,
and profiled with 512 image items of the maximum feature size.
...
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 16.81 GiB
```

Веса MedGemma 4B при этом занимают всего 4.58 ГиБ — то есть ~38 ГБ из 42 съел фиктивный прогон, а не модель.

При `16384` профилировка берёт 64 изображения, пик падает примерно с 38 ГБ до 5 ГБ.

**Как выбирать:** прикиньте худший реальный запрос. Бэкенд шлёт текст промпта плюс до `LIMIT_MM_PER_PROMPT` фотографий. 10 фото × 256 = 2560 токенов, плюс системный промпт, анамнез и место под ответ. 16384 даёт кратный запас. Ставить 131072 «на всякий случай» — прямой путь к OOM.

### `LIMIT_MM_PER_PROMPT`

> Дефолт: 1 изображение на промпт · У нас: `image=10`

Сколько мультимодальных объектов допустимо в одном запросе. Формат — `image=N`, можно перечислять модальности через запятую (`image=10,video=1`).

Критично для нашего сценария: бэкенд кладёт в один запрос список фотографий скана. При дефолтном лимите в 1 изображение запросы с несколькими фото будут отклоняться движком — уже в рантайме, а не на старте.

Значение должно быть не меньше `scanPhotoMaxNumber` из `application.json` (сейчас 6). Стоит с запасом — 10.

### `MAX_NUM_SEQS`

> Дефолт: `256` · У нас: `16`

Максимум последовательностей, которые движок батчит за одну итерацию. Фактически — потолок одновременных запросов на воркере.

Влияет на память: чем больше батч, тем больше активаций и KV-кэша нужно одновременно. Для нашей нагрузки (один врач — один запрос, тяжёлые мультимодальные промпты) 256 бессмысленно много. 16 оставляет место под всплеск, не раздувая профилировку.

### `GPU_MEMORY_UTILIZATION`

> Дефолт worker-vllm: `0.95` · У нас: `0.90`

Доля VRAM, которую vLLM разрешено занять под веса и KV-кэш. Остаток остаётся на активации, фрагментацию и CUDA-контекст.

**Важно понимать, чего эта настройка не делает.** Она не спасает от OOM на профилировочном прогоне: размер KV-кэша считается **после** профилировки, а падение происходит внутри неё. Понижать её в ответ на «CUDA out of memory» при старте — бесполезно, лечится это через `MAX_MODEL_LEN`.

0.90 против 0.95 — просто чуть больше воздуха на пики активаций.

### `TENSOR_PARALLEL_SIZE`

> Дефолт: `1` · У нас: `1`

На сколько GPU шардировать модель. **Обязан совпадать с `gpuCount`** эндпоинта — иначе воркер либо не найдёт нужные карты, либо оставит часть простаивать.

Нужен, только когда модель не влезает в одну карту. MedGemma 4B — это 8 ГБ весов, она свободно живёт на 24-гиговой L4; `TENSOR_PARALLEL_SIZE=2` для неё означает вдвое более дорогой воркер плюс NCCL-оверхед на каждом шаге генерации, без выигрыша.

### `ENABLE_PREFIX_CACHING`

> Дефолт: `false` · У нас: `true`

Кэширует KV общего префикса между запросами. Системный промпт (`backend/main/app/prompt/ru.py`, ~950 токенов) одинаков во всех обращениях, и без кэша его префилл пересчитывается каждый раз заново.

Выигрыш умеренный — префилл это малая часть времени по сравнению с генерацией, — но включение бесплатное и на результат не влияет: кэшируется вычисленное, а не угаданное.

### `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS` — пробовали, не помогло

> Дефолт: `1` (включено) · У нас: **не задаём**

Переменная самого vLLM, не аргумент движка. При старте движок профилирует CUDA-графы и вычитает их размер из бюджета KV-кэша.

Блок занимает 80–100 секунд холодного старта ради оценки в 0.08 ГиБ, и выглядит очевидным кандидатом на отключение. **Это не работает:** флаг влияет только на учёт, а сама профилировка выполняется всё равно. Замер до и после:

| | С профилировкой | С `=0` |
|---|---|---|
| Блок `Profiling CUDA graph memory` | 83 с | 98 с (выполнился) |
| Available KV cache | 5.71 ГиБ | 5.79 ГиБ |

Единственный эффект — плюс 0.08 ГиБ кэша, ровно размер неучтённой оценки. При этом vLLM выдаёт предупреждение, что память CUDA-графов больше не учитывается и это может потребовать снижения `GPU_MEMORY_UTILIZATION` во избежание OOM.

Не задавайте её: риск OOM ради 1.4% KV-кэша не окупается.

### `TRUST_REMOTE_CODE`

> Дефолт: `false` · У нас: `false`

Разрешает выполнять произвольный Python-код из репозитория модели на Hugging Face. Нужен для архитектур, которых нет в самом vLLM.

Для моделей Google это не требуется. Держим выключенным: это запуск чужого кода внутри контейнера, который обрабатывает медицинские данные.

### `HF_TOKEN`

> Дефолт: нет · У нас: `${HF_TOKEN}` из `secrets/.env`

Токен Hugging Face. MedGemma — gated-репозиторий: без токена (и без принятой лицензии на аккаунте) веса не скачаются, и воркер упадёт на загрузке.

### Что ещё можно добавить

Не задано сейчас, но пригодится:

| Переменная | Зачем |
|---|---|
| `QUANTIZATION` | `fp8`/`awq`/`gptq` — ужимает веса, экономит 30–50 % VRAM ценой небольшой потери качества |
| `KV_CACHE_DTYPE` | `fp8` — вдвое меньше KV-кэша, больше одновременных запросов |
| `DTYPE` | По умолчанию `auto`; явный `bfloat16` страхует от загрузки в float32 |
| `ENFORCE_EAGER` | `true` отключает CUDA-графы: меньше памяти, медленнее генерация. Аварийная мера при нехватке VRAM |
| `MAX_NUM_BATCHED_TOKENS` | Ещё один потолок размера батча, если `MAX_NUM_SEQS` недостаточно |

## Часть 3. Настройки эндпоинта

### `gpuTypeIds`

> Дефолт: нет · У нас: `["NVIDIA L4", "NVIDIA RTX A5000", "NVIDIA A40"]` для 4B, `["NVIDIA H100 80GB HBM3", ...]` для 27B

Список допустимых типов GPU **в порядке приоритета**: RunPod берёт первый доступный. Строки должны совпадать точно — полный список в [справочнике GPU](https://docs.runpod.io/references/gpu-types).

Минимум VRAM = веса + KV-кэш + активации. Ориентир для bf16:

| Модель | Веса | Минимальная карта |
|---|---|---|
| MedGemma 4B | ~8 ГБ | 24 ГБ (L4, RTX A5000) |
| MedGemma 27B | ~54 ГБ | 80 ГБ (H100, A100 80GB) |

Порядок в списке — это компромисс цены и скорости. L4 дешевле A40, но заметно медленнее; поставив её первой, вы экономите на типовой нагрузке и имеете запасные варианты, когда дешёвых карт нет в наличии.

Если оставить список пустым, RunPod может поднять воркер на карте, куда модель не влезет — ровно так и получился исходный OOM на 48-гиговой A40.

### `gpuCount`

> Дефолт: `1` (минимум 1) · У нас: `1`

Число GPU на воркер. Должен совпадать с `TENSOR_PARALLEL_SIZE`.

### `workersMin`

> Дефолт: не задан · У нас: `1` · В UI RunPod называется **Active workers**

Сколько воркеров держать всегда запущенными.

`0` — платите только за время выполнения запроса, но первый запрос после простоя оплачивает холодный старт: скачивание образа, загрузка весов, профилировка. По логам это десятки секунд.

`1` — мгновенный отклик ценой круглосуточной оплаты карты. Это главный рычаг «задержка против счёта», и он же самый дорогой параметр во всём конфиге: воркер тарифицируется всё время, а не только на запросах.

Задан в `defaults`, то есть действует на **все три** эндпоинта — включая 27B на H100. Если постоянно тёплой нужна только базовая модель, добавьте тяжёлым моделям перекрытие `"workersMin": 0` в их блоке `endpoints`.

При `workersMin ≥ 1` меняется смысл `idleTimeout`: он начинает управлять только гашением воркеров **сверх** минимума, а базовый живёт всегда.

### `workersMax`

> Дефолт: не задан · У нас: `3`

Потолок одновременных воркеров. Защита от неожиданного счёта: три воркера — максимум, во что может обойтись всплеск нагрузки.

### `scalerType` и `scalerValue`

> Дефолты: `QUEUE_DELAY` и `4` (минимум 0.5) · У нас те же

Как принимается решение поднять ещё воркер.

- `QUEUE_DELAY` — `scalerValue` это **секунды**: запрос провисел в очереди дольше — поднимается новый воркер.
- `REQUEST_COUNT` — `scalerValue` это **делитель**: количество запросов в очереди делится на него, получается желаемое число воркеров.

`QUEUE_DELAY` + 4 означает: терпим до 4 секунд ожидания, дальше масштабируемся. Для инференса, который сам по себе идёт десятки секунд, это адекватно — 4 секунды в очереди на фоне 30 секунд генерации погоды не делают, а лишний холодный старт стоит дорого.

### `idleTimeout`

> Дефолт: `5` (от 1 до 3600) · У нас: `30`

Сколько секунд воркер живёт без работы, прежде чем его погасят. Это оплачиваемое время.

Прямой компромисс: длиннее — больше запросов попадёт в «тёплый» воркер и ответит быстро; короче — меньше счёт. 30 секунд выбраны в расчёте на то, что врач редко делает одно исследование: следующий запрос в течение полуминуты попадёт на живой воркер и сэкономит холодный старт, который стоит дороже 30 секунд простоя.

### `executionTimeoutMs`

> Дефолт: не задан · У нас: `600000` (10 минут)

Максимум на один запрос. По истечении воркер останавливается, запрос помечается неуспешным. Страховка от зависшего инференса, который иначе жёг бы деньги.

**Смотрите на всю цепочку таймаутов**, а не на этот в отдельности:

| Звено | Лимит | Где задан |
|---|---|---|
| iOS | 300 с | `network` в `application.json` |
| Бэкенд → RunPod | **120 с** | `httpx.AsyncClient(timeout=120)` в `backend/main/app/main.py` |
| RunPod | 600 с | `executionTimeoutMs` |

Связывающее ограничение — 120 секунд на бэкенде. Остальные два никогда не сработают раньше, и при холодном старте пользователь получит 502, хотя RunPod продолжает считать.

### `flashboot`

> Дефолт: не задан · У нас: `true`

Оптимизация холодного старта RunPod: состояние воркера кэшируется, чтобы следующий запуск был быстрее. Учитывая, что при `workersMin: 0` холодный старт — основной источник задержки, включено.

Особенность: RunPod принимает это поле на запись, но **не возвращает** его в `GET /endpoints`. Поэтому скрипт отправляет его при создании, но исключает из сравнения — иначе каждый `apply` видел бы мнимое расхождение `None → true` и дёргал бесполезный PATCH.

### `dataCenterIds`

> Дефолт: список из 28 дата-центров · У нас: не задан

Где физически размещать воркеры. По умолчанию доступны все регионы — так выше шанс найти свободную GPU.

Сузить стоит, если появятся требования к резидентности данных: сейчас медицинские снимки могут уехать в любой из дефолтных регионов, включая США и Азию.

## Что скрипт не умеет

Скрипт синхронизирует фиксированный набор полей. Всё остальное из API будет **молча проигнорировано**, даже если вы это впишете в конфиг:

**Шаблон:** только `imageName`, `containerDiskInGb`, `env`. Игнорируются `dockerStartCmd`, `dockerEntrypoint`, `ports`, `volumeInGb`, `containerRegistryAuthId`.

**Эндпоинт:** `gpuTypeIds`, `gpuCount`, `workersMin`, `workersMax`, `scalerType`, `scalerValue`, `idleTimeout`, `executionTimeoutMs`, `flashboot`, `dataCenterIds`. Игнорируются `allowedCudaVersions`, `minCudaVersion`, `networkVolumeIds`.

Нужное добавляется в списки `TEMPLATE_FIELDS` / `ENDPOINT_FIELDS` в начале `runpod_sync.py`.

Ещё две особенности сравнения:

- **`env` сверяется по подмножеству.** Переменные, которых нет в вашем конфиге, скрипт не трогает — иначе RunPod-овские `RUNPOD_*` вызывали бы вечный дифф. Обратная сторона: удаление ключа из конфига не удалит его в RunPod, скрипт просто перестанет за ним следить.
- **Поля, не заданные в конфиге, не сравниваются.** RunPod применит к ним свои дефолты, а ручные правки в UI переживут `apply`.

## Шпаргалка

| Симптом | Что крутить |
|---|---|
| `CUDA out of memory` при старте, в стеке `siglip` / визуальный энкодер | Понизить `MAX_MODEL_LEN` — почти всегда только это |
| `CUDA out of memory` при загрузке весов | Карта побольше в `gpuTypeIds`, либо `QUANTIZATION=fp8` |
| `no kernel image is available for execution on the device` | Образ не знает архитектуру доставшейся карты. Свежий тег в `imageName` и/или сузить `gpuTypeIds`. К памяти отношения не имеет |
| Запрос с несколькими фото отклоняется движком | Поднять `LIMIT_MM_PER_PROMPT` |
| Первый запрос после паузы идёт очень долго | `workersMin: 1` (Active workers), либо увеличить `idleTimeout` |
| Счёт больше ожидаемого | Понизить `idleTimeout`, `workersMax`, взять более дешёвую карту |
| Очередь растёт под нагрузкой | Поднять `workersMax`, понизить `scalerValue` |
| Бэкенд отдаёт 502 на долгом инференсе | Таймаут `httpx` в `backend/main/app/main.py`, а не `executionTimeoutMs` |
| Воркер не может скачать веса | `HF_TOKEN` в `secrets/.env` + принятая лицензия модели на HF |
| `apply` каждый раз показывает изменения | Поле не возвращается в `GET` — исключить из диффа, как `flashboot` |
