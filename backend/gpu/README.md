# backend/gpu — сервис инференса на GPU-виртуалке

Отдельный сервис, который разворачивается **на GPU-виртуалке** рядом с самой моделью. Держит локальный vLLM, принимает от бэкенда готовую пару промптов со снимками, генерирует заключение и отдаёт его обратно.

## Как это устроено

```
                                   ┌─────────────────────────────────────────┐
                                   │  GPU-виртуалка (одна на модель)         │
                                   │                                         │
  iOS ──► backend/main ───────────►│  backend/gpu ──► vllm (localhost)       │
          (не-GPU виртуалка)       │  App Check       google/medgemma-4b-it  │
             │                     └─────────────────────────────────────────┘
             │
             └── fallback ────────► RunPod serverless
```

- **backend/main** ([`../main`](../main)) — не-GPU виртуалка. Собирает промпт, выбирает модель, маршрутизирует запрос. Инференса не делает.
- **backend/gpu** (этот сервис) — по одной виртуалке на модель. Проверяет App Check и вызывает локальный vLLM.
- **RunPod** — резерв. Бэкенд идёт туда, только если GPU-виртуалка не ответила; см. [`../main/RUNPOD.md`](../main/RUNPOD.md).

Промпты, локализация и шаблоны остаются в бэкенде. Этот сервис получает готовый текст и ничего о предметной области не знает — поэтому резервный запрос в RunPod уходит ровно с теми же входными данными.

Бэкенд выбирает виртуалку по id модели через `backend/main/secrets/gpu_endpoint.json` (образец — [`../main/gpu_endpoint.example.json`](../main/gpu_endpoint.example.json)). Модель, для которой записи там нет, уходит в RunPod. Отсюда и способ переезжать по одной модели: подняли виртуалку — добавили строку.

## Почему App Check проверяется здесь

Это единственное место во всей цепочке, где токен проверяется. `backend/main` его не проверяет: он забирает заголовок `X-Firebase-AppCheck` из входящего запроса и **передаёт без изменений** дальше. Проверка стоит там, где лежит модель, — достучаться до порта по сети недостаточно, чтобы получить заключение: нужен валидный токен живого экземпляра приложения.

Поэтому `secrets/firebase_credentials.json` нужен именно здесь — в `backend/main` зависимости `firebase-admin` больше нет.

Ответы 401/403 от этого сервиса бэкенд **не** отправляет в RunPod: запрос, не прошедший App Check, не должен получить заключение обходным путём.

## API

| Метод | Путь | App Check | Описание |
|---|---|---|---|
| `POST` | `/v1/conclusion_generation` | да | Генерация одного заключения |
| `GET` | `/health` | нет | Готов ли движок (`503`, пока грузятся веса) |

`/health` намеренно вынесен из-под `/v1`, чтобы виртуалку можно было опрашивать инфраструктурой без учётных данных приложения. Наружу он отдаёт только id модели, который и так публично виден в списке моделей приложения.

Запрос:

```json
{
  "modelId": "google/medgemma-4b-it",
  "systemPrompt": "...",
  "prompt": "...",
  "photos": [{ "data": "<base64 JPEG>" }],
  "temperature": 0.3,
  "maxTokens": 2048
}
```

Ответ:

```json
{ "modelId": "google/medgemma-4b-it", "response": "## Протокол ультразвукового исследования ..." }
```

`modelId` сверяется с `SERVED_MODEL_ID`. Чужой id — `400`, а не молчаливая генерация не той моделью, которую выбрал врач.

Rate limiter здесь не нужен: единственный клиент — бэкенд, а он уже ограничивает по адресу клиента. Лимитер на этой стороне сложил бы всех врачей в одно ведро за единственным IP бэкенда.

## Развёртывание

1. Поставить на виртуалку Docker, NVIDIA-драйверы и NVIDIA Container Toolkit.
2. Скопировать репозиторий (достаточно каталога `backend/gpu/`).
3. Создать `backend/gpu/secrets/`:
   - `.env` — по образцу [`.env.example`](.env.example);
   - `firebase_credentials.json` — сервисный аккаунт Firebase.
4. Запустить:

```bash
make start-gpu        # docker compose --env-file backend/gpu/secrets/.env -f backend/gpu/docker-compose.yml up --build -d
make start-gpu-logs
make stop-gpu
```

`--env-file` обязателен: Compose подставляет `${VAR}` в самом `docker-compose.yml` только из своего env-файла — значения из секции `env_file:` сервисов для этого не видны.

Первый запуск качает веса с Hugging Face (для 4B — около 8 ГБ) и занимает минуты. Веса лежат в volume `huggingface` и переживают перезапуск, поэтому платится только первая загрузка. `healthcheck` у `vllm` имеет `start_period: 900s`, чтобы контейнер не считался нездоровым, пока модель ещё грузится.

Проверка:

```bash
curl http://localhost:8100/health
```

## Настройки vLLM

Ключевые значения по умолчанию перенесены из RunPod-конфига вместе с причинами — подробный разбор каждой настройки в [`../main/RUNPOD.md`](../main/RUNPOD.md), он полностью применим и здесь:

| Переменная | Значение | Зачем |
|---|---|---|
| `VLLM_MAX_MODEL_LEN` | `16384` | Ограничивает не только длину запроса, но и профилировочный прогон энкодера на старте. На дефолте модели (131072 у Gemma 3 / MedGemma) 4B-модель падает с OOM даже на 40-гиговой карте. |
| `VLLM_LIMIT_MM_PER_PROMPT` | `image=10` | Не меньше `ultrasound.scanPhotoMaxNumber` из `application.json` (сейчас 6). При дефолтном лимите в 1 изображение запросы с несколькими снимками отклоняются в рантайме. |
| `VLLM_MAX_NUM_SEQS` | `16` | Потолок одновременных запросов. 256 по умолчанию для нашей нагрузки бессмысленно много и раздувает профилировку. |
| `VLLM_GPU_MEMORY_UTILIZATION` | `0.90` | Запас на активации и фрагментацию. От OOM на старте не спасает — это лечится `VLLM_MAX_MODEL_LEN`. |
| `VLLM_TENSOR_PARALLEL_SIZE` | `1` | Обязан совпадать с числом GPU в виртуалке. |
| `VLLM_IMAGE` | пин тега | Образ определяет сборку CUDA. Карта новее сборки падает с `no kernel image is available for execution on the device` на первой же CUDA-операции. Пиньте тег, который реально загрузился на этой карте. |

## Разработка

```bash
cd backend/gpu
../../.venv311/bin/python -m ruff check app tests
../../.venv311/bin/python -m ruff format app tests
../../.venv311/bin/python -m mypy
../../.venv311/bin/python -m pytest
```

Зависимости — `requirements-dev.txt`. Сервис намеренно повторяет структуру `backend/main/` (`app/core`, `app/model`, `app/route`, `app/service`) и дублирует `logging.py`: общего пакета между двумя разными деплоями нет, а файл маленький и меняется редко. `app_check.py` не дублируется — он существует только здесь.
